## Что выяснилось при первом запуске (29.08.2026)

Три вещи, которые не видны по коду и всплыли только на живых данных:

1. **Трекер терял 83% сделок.** Data API публикует сделки не потоком, а
   пачками раз в ~5 минут (голова стоит, потом прыгает на +300 сек,
   ~7800 сделок разом). `DATA_API_BATCH_LIMIT=200` покрывал 8 секунд —
   всё остальное отсекал чекпоинт, молча. Замер: из 975 сделок в окне в
   базу попадало 168. После `BATCH_LIMIT=10000` — потери 0.00% на окне в
   3994 сделки. **Не понижай этот параметр**, не замерив покрытие заново.
2. **Фильтр категорий был мёртв.** Gamma больше не заполняет поле
   `category` (null и у рынка, и у события), поэтому `IGNORED_CATEGORIES`
   не срабатывал: из первых 15 сигналов 10 пришли по спорту и киберспорту.
   Теперь категория берётся из тегов (`include_tag=true`), и детектор
   сверяет весь набор тегов. После фикса за 7 минут — один сигнал, по
   политике.
3. **Токен бота утекал в логи.** aiohttp вкладывает полный URL в текст
   исключения, а URL Bot API содержит токен: любой таймаут к Telegram
   печатал секрет в консоль и в файл. Добавлен редактор логов
   (`_TokenRedactor` в `core.py`). Если у тебя остались старые логи —
   проверь их перед тем, как кому-то пересылать.

**Остаточное ограничение:** у части рынков тегов нет вообще (≈40 из 57 в
теневой выборке) — такие рынки фильтр категорий не классифицирует и
пропускает. Классифицировать их нечем, кроме как по тексту вопроса.

## Переход на скоринг (30.08.2026)

Детекция больше не цепочка И. Каждый признак даёт баллы, сигнал уходит выше
`SCORE_THRESHOLD`, разбивка приходит в сообщение и пишется в БД — и для
сигналов, и для всей теневой выборки. Смысл: измерить вклад каждого признака.
При И-фильтрации это было невозможно в принципе — до исхода доживали только
сделки, прошедшие все условия разом.

Что важно помнить:

- **Порог 58 — временный.** Подобран замером на первых данных (~3 сигнала в
  час). Примерно через 3 дня работы включатся признаки кошелька (новизна,
  кластер), баллы вырастут — порог надо поднять, иначе будет поток.
  Перекалибровать: `python tools\calibrate_score.py`.
- **На молодой БД признаки кошелька выключены** намеренно: при истории в
  1.4 часа новыми выглядели 95% кошельков, и скоринг выдал 23 сигнала за
  7 минут. Пока история короче 3 дней, балл держится на признаках потока.
- **Прежняя Ветка A считается параллельно** и пишется в
  `shadow_trades.passed_filters`. Когда накопятся исходы, `tools/shadow_report.py`
  покажет, кто кого — старая методика или новая.
- **Появились тесты**: `python -m pytest tests\ -q`, 44 штуки.

## Ограничения, о которых легко забыть

1. **«Новизна» кошелька считается только по локальной БД.** С пустой БД ВСЕ
   кошельки выглядят новыми → Ветка A первые 2–4 недели шумит. Поэтому
   стартовые пороги задраны (`MIN_TRADE_USDC=2000`, `CLUSTER_MIN_WALLETS=3`),
   а реальные сигналы первое время даёт Ветка B (whitelist).
2. **Whitelist собран 05.05.2026** — за 3.5 месяца winrate адресов мог
   поехать. Перед тем как доверять Ветке B, прогони скоринг заново.
3. **Winrate 100% у 11 из 16 адресов — красный флаг методики.** Метрика
   «REDEEM по conditionId = выигрыш, BUY без REDEEM = проигрыш» не видит
   позиций, проданных до резолва, и завышает winrate. Считай эти цифры
   ранжированием, а не вероятностью.
4. **Схема БД от v0.1 несовместима** — старые `tracker.db` с ончейн-листенера
   не подходят (сменился PRIMARY KEY у `trades`).
