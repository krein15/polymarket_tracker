## Сделано ✅

### 0.1 — переезд на Data API (v0.2)
28.04.2026 Polymarket мигрировал на CTFv2, ончейн-листенер (`onchain.py`) умер.
Переписали на `https://data-api.polymarket.com/trades`: ушли RPC, web3,
ABI-декодирование; сделки приходят с `title`, `outcome`, `pseudonym`.

### 0.2 — обслуживание БД
`tools/db_maintenance.py`: онлайн-бэкап через SQLite Backup API (безопасен на
работающем трекере), ротация 14 копий, retention старых `trades`, VACUUM.
Вызывается из `scripts/backup_db.bat`, который дёргается перед каждым стартом.

### 0.3 — shadow tracker
Таблица `shadow_trades`: пишем **все** покупки ≥ `MIN_TRADE_USDC` на рынках
с volume24h ≤ `SHADOW_MAX_VOLUME_24H` — и прошедшие фильтры Ветки A, и
отброшенные. Резолвятся одинаково. Отчёт — `tools/shadow_report.py`.
Смысл: измерить **false negatives**, а не любоваться на прошедшие сигналы.

### 1.2 — outcome tracker
`signal_outcomes` + фоновая задача: снапшоты цены через 1ч / 24ч / 7д,
min/max за время жизни, при резолве — `settled_price`, `trader_was_right`,
`roi_if_followed`, `hours_to_resolve`. Троттлинг: молодые записи каждые
5 минут, «висяки» старше 30 дней — раз в сутки.

### 2.1 / 2.2 — метрики
Winrate против breakeven-winrate (для BUY ≈ средняя цена входа), медианный и
средний ROI, доверительный интервал Уилсона, разбивка по зонам цены входа,
по категориям, по размеру. В `tools/stats.py`, `tools/shadow_report.py` и в
командах Telegram-бота.

## Дальше — по приоритету

### 1. Набрать выборку (это блокирует всё остальное)
Нужно **≥100 закрытых (`market_resolved=1`) записей** в `shadow_trades` и
желательно ≥30 в `signal_outcomes`. Ничего не крутить, просто дать поработать.

Проверять раз в неделю:

```cmd
python tools\shadow_report.py
python tools\stats.py
```

### 2. Ответить на главный вопрос
**Фильтры Ветки A отбирают alpha или режут наугад?**
Сравнить winrate/ROI отброшенных (`passed_filters=0`) и пропущенных (`=1`)
при достаточном n:

- у пропущенных заметно лучше → фильтры работают, можно осторожно ослаблять
  пороги ради объёма сигналов;
- разницы нет → Ветка A в текущем виде бесполезна. Тогда либо резать её
  целиком и жить на whitelist, либо менять признаки (не «новизна кошелька»,
  а, например, скорость набора позиции или отклонение от цены рынка).

Смотреть отдельно `--by-zone`: возможно, alpha есть только в конкретном
диапазоне цены входа (типично — дешёвые хвосты < 0.20).

### 3. Пересобрать whitelist
`data/whitelist.txt` собран 05.05.2026, полгода — большой срок для трейдера.

```cmd
python tools\analyze_whitelist.py
```

И заодно **починить методику**: сейчас winrate = «REDEEM по conditionId /
все завершённые conditionId». Позиции, проданные до резолва, считаются
проигрышем, отсюда нереалистичные 100%. Надо учитывать SELL-активность и
считать не winrate, а реализованный PnL по conditionId.

### 4. Точный возраст кошелька (`/activity`)
Сейчас «новый кошелёк» = «мы его мало раз видели», из-за чего первые недели
после сброса БД Ветка A шумит. Polymarket отдаёт историю активности адреса —
запрашивать её при первой встрече кошелька и кэшировать в `wallets`
(`api_first_trade_ts`). Даёт настоящий возраст с первой же сделки.

### 5. Feedback-петля в Telegram
В `signals` уже есть колонка `user_feedback`, она никем не заполняется.
Повесить inline-кнопки 👍/👎 под сигналом → писать оценку в БД → в
`tools/stats.py` сравнивать субъективную оценку с фактическим исходом.

### 6. Тесты
Тестов нет вообще. Минимум, что окупится: `anomaly_detector.evaluate`
(табличные кейсы на границах порогов) и `storage` (дедуп сделок, кластер,
финализация исхода) на in-memory SQLite. Без них любая правка фильтров —
проверка «на живых деньгах».

### 7. v0.4 — интеграция с торговым ботом
Только после того, как п.2 даст положительный ответ хотя бы по одной ветке:
передача сигнала в `polymarket_bot/` (SQLite-очередь или Redis), ограниченное
автоисполнение Ветки B, размер позиции по Kelly.

## Первые результаты замера цен — 25.09.2026

Четыре дня, 2924 снимка (713 в сутки, как задумано), 268 закрылось.
Трекер без падений, ретеншн держит 6.9 дня. Поток сделок вырос вдвое —
15.5 в секунду против 6, база 7.04 ГБ и выходит на плато.

### Случайный рынок нельзя купить на $2000

Главное, чего не ждали:

| | переплата за размер, медиана |
|---|---:|
| случайный рынок | **30.8%** |
| рынок, где только что прошла крупная сделка | **0.6%** |

Причина арифметическая: $2000 по цене 0.02 — это 100 000 долей, по 0.30 —
6 667, по 0.95 — 2 105. Книга столько не отдаёт.

    ордер $2000 с переплатой < 5% проходит у 23% рынков
    $2000 не наливаются вовсе                    у 32%

И торгуемость почти целиком сидит в дорогой половине шкалы:

| цена | торгуемы на $2000 |
|---|---:|
| 0.20–0.60 | 7–8% |
| 0.60–0.80 | 25% |
| 0.80–0.95 | 45% |
| 0.95+ | 55% |

Зона 0.60–0.70, ради которой всё затевалось, — ровно там, где случайные
рынки мелкие. Поэтому снимки теперь пишут цену налива на **$200, $500 и
$2000**: если перевес переживает $200, но не $2000, это тоже ответ —
просто про другой масштаб позиции.

Размер позиции при этом НЕ рычаг на сигнальных рынках: $500 даёт +4.5%,
$2000 +5.2%, $5000 +4.2% — разница в шуме. Они достаточно ликвидны.

### Детектор при равной цене не добавляет ничего

Проверка, которой давно не хватало. Если весь перевес объясняется тем, ПО
КАКОЙ ЦЕНЕ мы покупаем, то детектор — сложный способ купить фаворита.
Сравнение внутри теневой выборки, 52 426 закрывшихся покупок, обе группы
по цене трейдера:

| цена | сигнал был | сигнала не было | разница |
|---|---:|---:|---:|
| 0.30–0.50 | +0.42% | −0.56% | +0.97 пп |
| 0.50–0.65 | −1.01% | +1.13% | −2.13 пп |
| **0.65–0.80** | **+11.81%** | +1.98% | **+9.83 пп** |
| 0.80–0.90 | −6.16% | −0.18% | −5.98 пп |
| 0.90–0.98 | −0.94% | −0.23% | −0.71 пп |
| | | **итого** | **+1.29 пп** |

Полоса 0.65–0.80 выглядела находкой: n=396, ROI +11.81% [+6.27; +17.34].
Разбор состава: **289 из 358 — киберспорт**, то есть поток до 15.09. На
свежей половине в этой полосе 38 наблюдений и −2.8 пп.

Вывод осторожный: перевес детектора над ценой **не подтверждён**. Не
«опровергнут» — на свежих данных Ветка A почти молчит (17, 38 и 12
наблюдений по полосам), и проверять нечем. Но единственное, что выглядело
перевесом, оказалось старым киберспортом.

Быструю полосу эта проверка не покрывает (она не попадает в
`signal_types`). Отдельное сравнение по хешу сделки: 217 совпадений,
взвешенно **−6.22 пп**, но интервалы по полосам ±30–40 пп — не вывод, а
предупреждение.

### Выборка, которая нужна, выросла вчетверо

Ранние ончейн-сигналы с порогом 0.50:

71 сигнал за 4 дня (17 в сутки), из них **9 по цене выше 0.80** — прежнее

зависящий от настенных часов, однажды ломается сам.

## Ошибается ли рынок сам — новое направление, 21.09.2026

### Почему понадобилось

К этому дню закрылись восемь гипотез подряд, и все по одной причине:
перевес живёт в цене трейдера, а мы опаздываем от 2 до 29 минут. Узкие
источники финансирования, киберспорт, дешёвые входы, погоня как вход,
предсказание погони, репутация кошелька — это варианты одного вопроса
«как успеть за инсайдером», и ответ везде «никак».

Но в данных всё это время лежала проверка, которую никто не делал. Взять
**все** 38 669 закрывшихся покупок теневой выборки — без фильтров, без
отбора — и сравнить цену с фактической долей выигрышей:

| цена | сделок | цена | винрейт | перевес | ROI |
|---|---:|---:|---:|---:|---|
| 0.10–0.20 | 359 | 15.1% | 8.4% | **−6.7 пп** | **−44.4%** [−63.9; −25.0] |
| 0.20–0.40 | 3 135 | 33.4% | 31.1% | −1.4 пп | −4.7% |
| 0.40–0.60 | 12 520 | 50.4% | 50.8% | +0.4 пп | 0.0% |
| 0.60–0.70 | 4 536 | 64.4% | 68.3% | **+3.9 пп** | **+5.9%** [+3.8; +8.0] |
| 0.70–0.80 | 3 540 | 74.6% | 76.5% | +1.9 пп | +2.4% [+0.6; +4.3] |
| 0.85–0.90 | 1 861 | 87.2% | 89.1% | +1.8 пп | +2.1% [+0.4; +3.7] |

Это favourite-longshot bias — смещение, давно известное букмекерским и
предсказательным рынкам. Держится и без киберспорта, и на одном спорте.

Принципиально другое в нём вот что: **скорость не нужна**. Это не чужая
информация, которую надо успеть скопировать, а систематическая ошибка в
цене. За две минуты она никуда не убегает.

### Чего этим числам не хватает

Два возражения, оба серьёзные.

**Это сделки людей, а не цены.** Покупки по 0.65 — не то же самое, что
«все рынки, стоящие 0.65»: информированные покупатели кучкуются там, где
у них перевес, и часть тех +5.9% может быть их правотой.

С аутсайдерами довод работает наоборот: будь покупатели по 0.15
информированы, они бы выигрывали, а они теряют 44%. Отбор смещал бы
результат в плюс, а мы видим минус — значит переоценка аутсайдеров
настоящая. Но про зону 0.60–0.70 так сказать нельзя.

**Эффект мал, и его может съесть стоимость входа.** По нашим замерам
переплата к цене сделки: 2.0% в зоне 0.50–0.65, 3.2% в 0.65–0.80, 1.2%
выше 0.80. Тогда:

    0.60-0.70   +5.9% - 2.0%  =  +3.9%   переживает
    0.85-0.90   +2.1% - 1.2%  =  +0.9%   на грани
    0.70-0.80   +2.4% - 3.2%  =  минус   не переживает

### Что построено

`polymarket_tracker/price_sampler.py` — снимки цены САМИХ РЫНКОВ. Рынки
берутся из списка Gamma, отбор не зависит от цены, торговал там кто-то
или нет — неважно. Раз в час до 30 рынков, оба исхода отдельными
строками, ~700 рынков в сутки. Резолв — третьей целью в `_OutcomeTarget`,
рядом с боевой и теневой выборкой, без дубля правила.

Пишутся три цены, потому что это три разных вопроса:

    mid        ошибается ли рынок            (есть ли смещение вообще)
    best_ask   переживёт ли перевес спред    (первая сотня долларов)
    fill_2000  переживёт ли обход стакана    (реальный ордер $2000)

Отчёт — `tools/calibration.py`.

### Три ловушки, найденные на живых данных

1. **Первая страница списка Gamma — сплошь рынки 2027–2028 годов**, сто
   из ста улетали в отсев. Рамку теперь задаёт сам Gamma через
   `end_date_min`/`end_date_max`; фильтр по дате от цены не зависит.

2. **У крайних рынков своя сторона книги пуста**: у аутсайдера по 0.001
   нет бидов, у его фаворита по 0.999 — асков. Из 16 снимков у 10 не
   считалась середина, и все 10 — крайние цены. Это пропуск, СВЯЗАННЫЙ С
   ЦЕНОЙ, то есть ровно то смещение, ради борьбы с которым замер и
   затевался. Лечится объединением книг: бид на Yes по 0.001 — это ровно
   аск на No по 0.999. Где и после этого середины нет, опорой служит аск:
   позицию всё равно можно купить, а терять хвост шкалы нельзя.

3. **Подряд в списке лежат рынки одного события.** Первый живой проход
   записал 53 строки, и все 53 — одна категория: 27 рынков по кандидатам
   на выборах в Бразилии. Последовательный обход держал бы выборку на
   одном событии часами, а это не независимые наблюдения. Смещение
   страницы теперь случайное, граница учится по ответам API.

### Что дальше

- [ ] Дать набрать две недели, смотреть `python tools\calibration.py`
- [ ] Критерий тот же: **нижняя граница интервала ROI выше нуля**, и
      считать по `fill_2000`, а не по `mid`
- [ ] Проверить, совпадает ли безусловная выборка с теневой. Разойдутся —
      значит в теневой работает отбор информированных, и это само по себе
      результат
- [ ] Горизонт 30 дней записан в `end_date_ts`: проверить, не держится ли
      смещение только на коротких рынках

## Порог цены входа и починка погони — 21.09.2026

### Где живёт убыток: четверть сделок даёт 84% его

541 сигнал с замером достижимой цены и исходом, общий ROI −15.2%:

| наша цена | сделок | ROI у нас | ROI у трейдера | доля убытка |
|---|---:|---:|---:|---:|
| < 0.35 | 54 | −83.5% | −87.5% | **55%** |
| 0.35–0.50 | 81 | −29.4% | −38.2% | **29%** |
| 0.50–0.60 | 87 | −3.6% | +0.7% | 4% |
| 0.80–0.90 | 78 | +13.3% | +33.0% | −13% |

В дешёвой зоне в минусе **сам трейдер**: перевес −36.8 пп ниже 0.35 и
−19.3 пп на 0.35–0.50. Значит отсекается не наше опоздание, а его плохие
сделки. На потоке после 15.09 порог меняет −23.0% на −0.6%.

Сделано: `ENTRY_MIN_PRICE=0.50`, вердикт «не входить» приходит веткой к
сигналу через 2 минуты. Шлём только красный: часовой лимит сообщений один
на все ветки, и вердикт по каждому сигналу вытеснял бы сами сигналы.
**Молчание не значит «можно»** — замер мог не состояться.

Отвергнутая гипотеза: «цена упала после его сделки». При входе выше 0.50
падение не меняет ничего (−3.4% против −2.1%). Первая таблица показывала
лишь то, что дешёвые входы чаще бывают упавшими.

### Спорт выключили зря, но вернули не везде

Правка 15.09 ставила `IGNORED_CATEGORIES=crypto,sports`, а тег `sports`
стоит и на киберспорте, и на NFL. С порогом входа 0.50:

| | сделок | ROI у нас | перевес трейдера |
|---|---:|---:|---:|
| обычный спорт | 131 | **+3.5%** | +9.8 пп |
| киберспорт | 248 | −8.7% | +2.3 пп |

И главное: ранние ончейн-сигналы — 66 из 78 — это обычный спорт. Без него
единственная ветка, входящая по цене трейдера (переплата +0.5%), пустеет.

Теги сняты с живых рынков: `esports` стоит на lol/cs2/dota2 и ни на одном
обычном спорте. Поэтому `IGNORED_CATEGORIES=crypto,esports`.

Но **не для score**: у него данных по спорту нет вообще (33 237 сделок с
пустым баллом), а под порогом ликвидности их 720 в сутки — включение
вслепую дало бы сотню-другую сигналов в день. Отсюда
`SCORE_IGNORED_CATEGORIES=sports`. Замерять его очередь ещё придёт.

### Погоня мерила процент там, где цены живут в (0,1]

`CHASE_MIN_RATIO=0.25` требует, чтобы последователи заплатили на 25% выше
трейдера. При его цене выше 0.80 это требует VWAP больше единицы. Ветка не
видела 8851 размеченную сделку из 29 980.

| правило | сделок | ROI (его цена) | дороже 0.80 |
|---|---:|---:|---:|
| было: chase ≥ +25% | 591 | +84.2% | **0%** |
| стало: сдвиг ≥ +0.05 | 1479 | +48.1% | 10% |
| только дороже 0.80 | 155 | +13.2% [+9.4; +16.9] | 100% |

ROI ниже, но это ROI по ЕГО цене. Переплата падает вместе с ценой: медиана
9.0% ниже 0.35 и 1.2% выше 0.80. В дорогом рынке цене некуда убежать,
поэтому +13.2% достаются нам почти целиком, а +84.2% в дешёвом — нет: у
погони медиана переплаты там 59.4%, и по нашей цене она давала −10.5%.

Отбой зеркально: −0.05 ловит 454 разворота против 244, качество то же.

### Предсказать погоню в минуту 0 — не вышло (закрыто)

Замысел был такой: весь перевес проекта сидит в метке погони (+51.6% ROI
против +0.2% у всех покупок подряд), но метка приходит на 29 минут позже
сделки. Если предсказать её сразу, входить можно по цене трейдера.

Собрано 14 742 сделки с признаками момента сделки (`tools/chase_features.py`):
удар по цене к медиане за 30 мин, размер к потоку, активность и число
участников, разброс цен, история кошелька. Модель — `tools/chase_model.py`.

**Метку модель предсказывает хорошо, денег не даёт.** AUC 0.728 вне
выборки, доля погонь в верхнем дециле 34.4% против базовых 14.9% — а ROI
−2.4%. Причина видна, если печатать рядом долю разворотов:

| группа | погонь | разворотов | отношение |
|---|---:|---:|---:|
| все | 14.9% | 8.2% | 1.82 |
| верхние 5% по модели | 35.7% | 19.0% | 1.88 |
| нижние 30% | 3.8% | 3.4% | 1.12 |

Отношение не сдвигается. **Рыночные признаки предсказывают движение, а не
направление** — обе доли растут вместе, и на ROI это не сказывается.

Пробовали признак другой природы — репутацию кошелька («ходил ли рынок за
ним раньше»). На обучающей половине он отношение сдвигал, но вне выборки
развалился: группа «шли редко» дала +16.5% [+9.7; +23.3] на обучении и
**−59.4% [−77.0; −41.9]** на свежих данных.

Вывод: ценность погони — в том, КТО пошёл следом и по какой цене, а это до
их действий просто не существует. Направление закрыто. Инструменты
оставлены: метка растёт на ~100 сделок в сутки бесплатно, и если появится
источник данных о самих последователях, проверка займёт вечер.

Оговорка к свежей половине: из 3366 сделок закрылись 632, и это в основном
короткие рынки. Числа по ней шумнее, чем по обучающей.

осведомлённостью. Отчёт теперь печатает перевес над безубытком и нижнюю
границу, а не винрейт.

Инструмент оставлен: выборка растёт, повторить замер — одна команда
(`--reuse` считает по сохранённым источникам, без похода в сеть).

## Надзиратель за трекером (11.09.2026, сделано)

09-10.09 трекер простоял сутки: пусковой `.bat` запускал его ровно один
раз, процесс умер — и всё встало до ручного вмешательства. Обнаружилось
только при разборе логов.

Теперь простой стоит времени напрямую: чтобы отличить прибыль от нуля,
нужно порядка 700 закрывшихся сделок, около месяца, и каждые сутки
простоя добавляются к сроку.

`tools/supervise.py` поднимает трекер обратно. Правила:

- прожил больше получаса — падение считается случайным, счётчик неудач
  сбрасывается, поднимаем сколько угодно раз;
- падает мгновенно и подряд — пауза растёт (15 с → 10 мин), а после
  восьми таких падений надзиратель **сдаётся**. Вечный цикл на сломанном
  трекере хуже остановки: он выглядит работой, а данных не прибавляется;
- штатный выход (код 0) перезапуском не считается.

На Python, а не циклом в `.bat`, потому что надзирателю нужно мерить время
жизни процесса: перезапуск после получаса работы и после трёх секунд —
разные ситуации. Арифметика со временем в batch нечитаема и не проверяется
тестами.

## Агент-оценщик — ОТЛОЖЕН 16.09.2026

**Статус.** Инструменты написаны и покрыты тестами, замер калибровки не
начат. Отложен сознательно: на остаток бюджета (~$12) он не помещается, а
то, что уже видно, не обещает перевеса за полную цену замера.

**Идея.** Трекер спрашивал "кто-то знает больше рынка?" и копировал чужие
сделки — замер на 425 сделках дал -12.8%: перевес живёт в цене входа
трейдера, которой у нас нет. Агент оценивает вероятность сам и сравнивает
с ценой. Не "найти вероятного победителя" — это и есть цена, — а найти
рынок, где цена не учла уже известного.

**Главное правило конструкции: модель НЕ видит цену.** Покажи ей 0.72 —
напишет "около 70%", и мы измерим послушность вместо знания. Закреплено
тестом.

### Что показал пилот

**Модели расходятся между собой сильнее, чем с рынком.** Шесть рынков, обе

|---|---:|

| Opus 5 против рынка | 0.191 |

Это верхняя граница того, сколько в оценках сигнала.

0.01-0.02: модели не умеют назвать число мельче сотой. На дешёвом рынке это
выглядело бы двадцатикратным перевесом. Поэтому в отборе нижняя граница
цены 0.10.

**Связность на чистом наборе.** "Balance of Power: 2026 Midterms", три

## Достижимая цена входа (11.09.2026, сделано)

Всё, что мерилось до сих пор, считалось от цены ТРЕЙДЕРА. Но сигнал
приходит после того, как рынок за ним пошёл, — и уходит вверх ровно потому,
что пошёл. Пересчёт на цену последователей, 507 сделок с исходом:

| считаем от | ROI | 95% интервал | от нуля отличим |
|---|---:|---|---|
| его цены | +44.4% | — | — |
| цены последователей | **+4.2%** | [-1.7; +10.1] | **нет** |
| + проскальзывание 2% | +2.2% | [-3.7; +8.1] | нет |
| фавориты > 0.80 | +10.2% | [+7.4; +13.1] | да |

Перевес живёт в его цене входа, которой у нас нет. Поэтому теперь по
каждому сигналу пишется цена, по которой ордер РЕАЛЬНО налился бы
(`signal_entries`), — через `ENTRY_DELAY_SEC` (по умолчанию 120 с) после
отправки: увидеть сообщение, открыть рынок, нажать.

**Ловушка в API, стоившая бы целого спреда.** У Polymarket
`/price?side=buy` возвращает лучший БИД, а не аск. Проверено по стакану:
при биде 0.58 и аске 0.59 `side=buy` даёт 0.58, `side=sell` — 0.59.
Покупая, платишь аск. Ошибка в одну букву дала бы систематически заниженную
цену входа и завышенную прибыль — молча, без единого падения.

**Берётся книга целиком, а не верх.** Верх книги — цена первой сотни
долларов, а сигнальные сделки измеряются тысячами. На живом замере: аск
0.43, а ордер на $5000 наливается по 0.5896 — на 37% хуже. Записываются
цены налива для $500 / $2000 / $5000 сразу: если крупный размер заметно
дороже мелкого, стратегия не масштабируется, и это надо видеть. Чего в
стакане не было — не покупаем, поле остаётся пустым.

Отчёт: `python tools/paper_pnl.py --size 2000 --type chase`.

**Сколько ждать.** При наблюдаемом разбросе, чтобы отличить +5% от нуля,
нужно порядка 700 закрывшихся сделок — около месяца при текущем потоке.
Раньше цифры будут, но на сотне интервал шире самого эффекта.

## Снимки цены собирались смещённо (найдено и починено 10.09.2026)

Замеры дрейфа опираются на `price_1h` — цену через час после сделки. На
живых данных выяснилось, что колонка заполнена далеко не всегда, и пропуски
не случайны:

| рынок закрылся за | сделок | снимок через час есть |
|---|---:|---:|
| < 1 часа | 726 | 0.0% |
| 1-3 часа | 435 | 1.8% |
| 3-12 часов | 9992 | **12.7%** |
| 12-48 часов | 6512 | 35.0% |
| больше 2 суток | 507 | 98.4% |

Для рынков быстрее часа снимка и быть не может. Но 3-12 часов живут заметно
дольше часа — там 12.7% это потеря, причём **смещённая**: дрейф мерился
почти только по медленным рынкам, тогда как поток трекера — быстрый спорт.

**Причина.** Очередь на проверку была чистым LRU: «дольше всех не
проверявшиеся первыми». У свежей сделки `last_checked_ts` почти сейчас,
поэтому она уходила в самый хвост, а впереди стояли тысячи старых. Час
истекал раньше, чем до неё доходил черёд.

**Вторая половина той же беды.** Когда очередь всё-таки доходила до строки
через сутки, старый код записывал в `price_1h` текущую цену — суточной
давности вместо часовой. Поле называется «через час», а числом является
совсем другим. Ошибка не падает и не видна: колонка заполнена, замер
считается, числа выходят уверенные и неверные.

**Что сделано.** Половина батча отдаётся строкам, у которых снимок
просрочен, но ещё имеет смысл (допуск — само окно, для часа это до двух
часов); вторая половина остаётся обычной очереди, иначе проверка резолва
встала бы, пока разбирается хвост. Просроченное сверх допуска честно
остаётся пустым. Нагрузка на Gamma не изменилась: правится порядок, а не
число запросов.

**Оговорка про уже собранное.** Существующие значения `price_1h` собраны
старой логикой, и часть из них снята позже часа — какая именно, по данным
не определить: момент заполнения не хранится. Поэтому прошлые замеры дрейфа
(в том числе `price_impact`, +9.9 пп) стоит считать оценкой по медленным
рынкам, а не по всему потоку. Перепроверять их нужно на данных, собранных
уже после этой правки.

## Быстрая полоса из блокчейна (06.09.2026, сделано)

Слушаем OrderFilled обоих контрактов V2 через вебсокет Alchemy. Задержка
~1 секунда против 250-380 секунд у Data API.

Расшифровка сверена с Data API по шести сделкам: сумма, цена и токен
совпали во всех случаях. Событие опознаётся по форме (4 темы, 7 слов
данных), а не по хешу подписи — из трёх событий контракта такую форму
имеет только OrderFilled.

**Полоса ничего не пишет в таблицу trades.** У лога нет отметки времени
сделки, и подстановка текущего времени сделала бы запись на пять минут
"моложе" её же копии из Data API — поехали бы чекпоинт, часовые базовые
обороты и сторож простоя. Поэтому разделение: цепочка даёт ранний сигнал,
Data API остаётся системой учёта. Отвалится вебсокет — трекер работает
как раньше, просто без форы.

На ранней сделке считается один признак — удар по цене, единственный из
измеренных, который доступен мгновенно. Остальные (накопление, кластер,
история кошелька) требуют записей, которых ещё нет. Полная оценка придёт
позже обычным путём: ранний сигнал её не заменяет, а опережает.

Живая проверка: 11 252 события за 150 секунд, 6 463 расшифрованы,
53 крупнее $1000, 11 сигналов на тестовых порогах. У 42% кандидатов
опорной цены не нашлось (мало сделок в окне) — в таких случаях молчим,
а не гадаем.

## Разведка ончейна (06.09.2026)

**Скорость.** Голова цепочки отстаёт от реального времени на 0 секунд, наш
путь через Data API — на 250-380 секунд, причём это свойство API (он
публикует сделки пачками раз в 5 минут), а не наша медлительность.

Стоит ли гнаться за этими минутами — замерено:

| | первые 5 мин | 5-20 мин | через час |
|---|---:|---:|---:|
| все выигравшие (n=2103) | +1.3% | +3.0% | +15.5% |
| группа "рынок побежал" (n=142) | **+15.9%** | +37.2% | +64.2% |

В общей массе за первые пять минут уходит 8% движения — скорость почти не
решает. Но в той группе, ради которой всё делается, уходит **четверть**.
Опоздание на 5 минут там означает вход на 16% дороже.

Контракты V2 живые: CTF Exchange даёт ~40 событий в секунду, NegRisk ~17.
Адреса лежат в config.py.

**Граф финансирования — устройство сложнее, чем ожидалось.** Наивный
вопрос "кто прислал токены на кошелёк" ответа не даёт: pUSD приходит либо
чеканкой с нулевого адреса, либо с самих контрактов биржи.

Разбор транзакции показал реальную цепочку (213 событий в одной пакетной
транзакции релеера):

    0x4d97dcd9... --50 USDC.e--> шлюз --> pUSD чеканит 50 нашему кошельку

То есть настоящий источник денег виден, но на шаг глубже: нужно внутри
пакетной транзакции сопоставить перевод USDC с чеканкой по совпадению
суммы. Проверенный источник не оказался хот-кошельком биржи (ноль
исходящих за пять часов), значит личность спонсора несёт информацию.

**Публичные RPC для истории непригодны.** За одним URL стоит пул узлов:
тот же диапазон блоков то отдаётся, то отвечает "History has been pruned".
Для разовых свежих запросов годятся, для замера по истории — нет. Нужен
архивный доступ: индексный API Etherscan v2 (chainid=137; отдельный API
polygonscan.com больше не работает). На нём и живёт весь разбор
финансирования: `proxy&action=eth_getTransactionReceipt` отдаёт чек за
0.7 с, Alchemy для этого не нужен — его месячная квота ушла на вебсокет.

**Чего НЕ надо делать.** Внутренние транзакции и трассировка для задачи
"войти вместе с инсайдером" бесполезны: сделки видны в обычных логах
событий. Это отмечено, чтобы не всплыло снова как ложная цель.

## Что показали данные (06.09.2026, 568 боевых и 11 239 теневых исходов)

Первый разбор на выборке, которой уже можно верить. Записано, чтобы не
пересматривать по кругу.

**У скоринга в целом преимущества нет.** Winrate 58.6% при необходимых
58.6%. Оценка ползла вниз по мере накопления данных — 93% на 15 исходах,
70.7% на 123, 58.6% на 568. Первые две цифры были миражом малой выборки.

**Дешевизна входа сама по себе не улика.** Внутри зоны цены ниже 0.35 балл
не различал победителей: при 20-39 перевес -0.8 пп, при 40-59 стало хуже
(-3.8 пп). Хвост там есть (максимумы +693% и +490%), но наши признаки его
не находят. Признак `cheap_tail`, начислявший баллы просто за низкую цену,
убран: он смещал выборку в сторону лотерейных билетов, не добавляя знания.
Гейт по цене при этом НЕ ставился — отрезать зону значит закрыть тему, ради
которой трекер и делался.

**Дрейф цены после входа — рабочий ранний индикатор.** У сделок, которые
в итоге выиграли, цена через час +16.1%; у проигравших -28.1%. Это даёт
цикл обратной связи в час вместо недели: новые признаки можно проверять
не дожидаясь резолвов.

**Удар по цене работает.** Насколько сделка прошла выше медианы покупок за
предыдущие полчаса:

| переплата | n | дрейф через час | перевес |
|---|---:|---:|---:|
| больше +20% | 117 | +17.6% | +9.9 пп |
| около нуля | 1710 | +0.1% | -1.8 пп |
| ниже рынка (< -3%) | 148 | -23.5% | -10.3 пп |

Контроль на размер пройден: внутри корзины $1k-5k переплатившие дали
+14.9% дрейфа против -2.5% у остальных, а медианный размер у них даже
меньше ($3273 против $3623). То есть признак меряет агрессию входа, а не
величину сделки. Внедрён как `price_impact`: +20 за переплату свыше 20%,
-15 за вход ниже недавнего рынка. Средние корзины вели себя несогласованно
и баллов не дают.

**Главный вывод.** Все прежние признаки описывают ПОТОК (размер, объём,
число участников, ликвидность), а не ЗНАНИЕ. Поэтому в среднем и получался
обычный рынок — мы его и измеряли. `price_impact` — первый признак про
поведение информированного участника, и первый, показавший перевес.

Пункты 1–5 из списка ниже реализованы: детекция переведена на скоринг
(`polymarket_tracker/scoring.py`), добавлены накопление позиции, сравнение с

Прежняя Ветка A сигналов не шлёт, но её вердикт пишется рядом с баллом —

Что выяснилось сразу на живом потоке: на молодой БД признаки кошелька дают

### Считается на уже накопленных данных (новых источников не нужно)

**1. Накопление позиции вместо разовой сделки.** Сейчас порог `MIN_TRADE_USDC`
применяется к одной сделке. Тот, кто набирает $6000 двадцатью сделками по $300
за десять минут, невидим — а это ровно то, как ведёт себя аккуратный инсайдер.
Нужно агрегировать по `(кошелёк, рынок)` в скользящем окне и сравнивать порог
с суммой. Данные уже в таблице `trades`, это чистая доработка детектора.
Скорее всего, самый крупный пропуск из всех.

**2. Аномалия относительно самого рынка, а не абсолютный порог.**
`MAX_MARKET_VOLUME_24H=50000` — константа, одинаковая для рынка с оборотом
$300/день и $40000/день. Настоящий сигнал: рынок, где обычно $500 в сутки,
за десять минут увидел $5000. Считается как z-score текущего часа против
медианы за 7 дней по этому же рынку — вся история есть локально.

**3. Пробуждение спящего кошелька.** Кошелёк молчал 60 дней и внезапно берёт
крупно — сильный признак, ортогональный «новизне». Сейчас такой трейдер
проходит как «обычный» и отсекается. Считается по `wallets.last_seen_ts`.

**4. Отсев маркет-мейкеров и арбитражников.** Кошелёк, который торгует обе
стороны одного рынка или сидит в сотне рынков сразу, — не инсайдер, но на
старте базы выглядит «новым». Простое правило: если по рынку есть и buy, и
sell от одного адреса — не сигналить.

**5. Скоринг вместо жёсткого И.** Заменить цепочку фильтров на взвешенную
сумму признаков (размер относительно рынка, новизна, концентрация, пробуждение,
кластер, зона цены) и слать сигнал выше порога, показывая разбивку в сообщении.
Это не только повышает полноту — это делает теневой анализ осмысленным:
станет видно, **какой именно признак** несёт alpha, а какой шумит. Сейчас,
при И-фильтрации, вклад отдельного условия измерить нельзя в принципе.

### Требует нового источника данных

**6. Агрессия по стакану (CLOB API).** Инсайдер снимает ликвидность, а не
ставит лимитку: переплачивает относительно середины спреда и двигает цену.
Сравнение цены сделки с лучшим bid/ask до неё отделяет «уверен» от «зашёл
по рынку заодно». Нужен `clob.polymarket.com/book`.

**7. Граф финансирования кошельков (Polygonscan/RPC).** Классическая подпись
инсайдера: несколько свежих кошельков, залитых с одного адреса, синхронно
берут один исход. Кластер сейчас считает просто «N новых кошельков», без связи
между ними — а связь и есть главное. Именно так публично находили инсайдеров
на Polymarket. Нужен внешний API по транзакциям Polygon.

**8. Концентрация относительно самого кошелька (`/positions`).** Ставка в 80%
своего портфеля — совсем не то же самое, что те же $5000 у кита с миллионом.
Data API отдаёт позиции по адресу.

Методика отбора whitelist завышает winrate: позиция, проданная до резолва,

## Сознательно НЕ делаем

- **Не понижаем пороги «на глаз»**, пока нет выборки. Каждое изменение
  фильтра обнуляет сопоставимость накопленных данных.
- **Не переписываем на ончейн-листенер.** Data API абстрагирует апгрейды
  контрактов; адреса V2 лежат в `config.py` на случай, если API отвалится.
- **Не усложняем детектор новыми признаками**, пока не измерены текущие.
