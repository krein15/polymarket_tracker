## Сделано ✅

### 0.1 — переезд на Data API (v0.2)
28.04.2026 Polymarket мигрировал на CTFv2, ончейн-листенер (`onchain.py`) умер.
Переписали на `https://data-api.polymarket.com/trades`: ушли RPC, web3,
ABI-декодирование; сделки приходят с `title`, `outcome`, `pseudonym`.

### 0.2 — обслуживание БД
`tools/db_maintenance.py`: онлайн-бэкап через SQLite Backup API (безопасен на
работающем трекере), ротация 14 копий, retention старых `trades`, VACUUM.
Вызывается из `scripts/backup_db.bat`, который дёргается перед каждым стартом.

### 0.3 — shadow tracker
Таблица `shadow_trades`: пишем **все** покупки ≥ `MIN_TRADE_USDC` на рынках
с volume24h ≤ `SHADOW_MAX_VOLUME_24H` — и прошедшие фильтры Ветки A, и
отброшенные. Резолвятся одинаково. Отчёт — `tools/shadow_report.py`.
Смысл: измерить **false negatives**, а не любоваться на прошедшие сигналы.

### 1.2 — outcome tracker
`signal_outcomes` + фоновая задача: снапшоты цены через 1ч / 24ч / 7д,
min/max за время жизни, при резолве — `settled_price`, `trader_was_right`,
`roi_if_followed`, `hours_to_resolve`. Троттлинг: молодые записи каждые
5 минут, «висяки» старше 30 дней — раз в сутки.

### 2.1 / 2.2 — метрики
Winrate против breakeven-winrate (для BUY ≈ средняя цена входа), медианный и
средний ROI, доверительный интервал Уилсона, разбивка по зонам цены входа,
по категориям, по размеру. В `tools/stats.py`, `tools/shadow_report.py` и в
командах Telegram-бота.

## Дальше — по приоритету

### 1. Набрать выборку (это блокирует всё остальное)
Нужно **≥100 закрытых (`market_resolved=1`) записей** в `shadow_trades` и
желательно ≥30 в `signal_outcomes`. Ничего не крутить, просто дать поработать.

Проверять раз в неделю:

```cmd
python tools\shadow_report.py
python tools\stats.py
```

### 2. Ответить на главный вопрос
**Фильтры Ветки A отбирают alpha или режут наугад?**
Сравнить winrate/ROI отброшенных (`passed_filters=0`) и пропущенных (`=1`)
при достаточном n:

- у пропущенных заметно лучше → фильтры работают, можно осторожно ослаблять
  пороги ради объёма сигналов;
- разницы нет → Ветка A в текущем виде бесполезна. Тогда либо резать её
  целиком и жить на whitelist, либо менять признаки (не «новизна кошелька»,
  а, например, скорость набора позиции или отклонение от цены рынка).

Смотреть отдельно `--by-zone`: возможно, alpha есть только в конкретном
диапазоне цены входа (типично — дешёвые хвосты < 0.20).

### 3. Пересобрать whitelist
`data/whitelist.txt` собран 05.05.2026, полгода — большой срок для трейдера.

```cmd
python tools\analyze_whitelist.py
```

И заодно **починить методику**: сейчас winrate = «REDEEM по conditionId /
все завершённые conditionId». Позиции, проданные до резолва, считаются
проигрышем, отсюда нереалистичные 100%. Надо учитывать SELL-активность и
считать не winrate, а реализованный PnL по conditionId.

### 4. Точный возраст кошелька (`/activity`)
Сейчас «новый кошелёк» = «мы его мало раз видели», из-за чего первые недели
после сброса БД Ветка A шумит. Polymarket отдаёт историю активности адреса —
запрашивать её при первой встрече кошелька и кэшировать в `wallets`
(`api_first_trade_ts`). Даёт настоящий возраст с первой же сделки.

### 5. Feedback-петля в Telegram
В `signals` уже есть колонка `user_feedback`, она никем не заполняется.
Повесить inline-кнопки 👍/👎 под сигналом → писать оценку в БД → в
`tools/stats.py` сравнивать субъективную оценку с фактическим исходом.

### 6. Тесты
Тестов нет вообще. Минимум, что окупится: `anomaly_detector.evaluate`
(табличные кейсы на границах порогов) и `storage` (дедуп сделок, кластер,
финализация исхода) на in-memory SQLite. Без них любая правка фильтров —
проверка «на живых деньгах».

### 7. v0.4 — интеграция с торговым ботом
Только после того, как п.2 даст положительный ответ хотя бы по одной ветке:
передача сигнала в `polymarket_bot/` (SQLite-очередь или Redis), ограниченное
автоисполнение Ветки B, размер позиции по Kelly.

## Сознательно НЕ делаем

- **Не понижаем пороги «на глаз»**, пока нет выборки. Каждое изменение
  фильтра обнуляет сопоставимость накопленных данных.
- **Не переписываем на ончейн-листенер.** Data API абстрагирует апгрейды
  контрактов; адреса V2 лежат в `config.py` на случай, если API отвалится.
- **Не усложняем детектор новыми признаками**, пока не измерены текущие.
